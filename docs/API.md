# Item Manager API

REST API for the Item Manager shop app (device repairs, order numbers `TPB-xxxxx`).
It is the backend for the Flutter mobile front end. The web app (Laravel 12 +
Livewire) and the API share the same code, the same database and the same
rules: nothing is duplicated, the API reuses `DevicePolicy`,
`StoreDeviceRequest` / `UpdateDeviceRequest` and the `Device` query scopes.

- Base URL (production): `https://item-manager.thephoneboss.net`
- Current version: **v1** — every endpoint lives under `/api/v1`
- Full machine-readable spec: [`API_V1_OPENAPI.yaml`](API_V1_OPENAPI.yaml) (OpenAPI 3.0, Swagger)
- Postman collection: [`API_V1_POSTMAN.json`](API_V1_POSTMAN.json)

## Versioning

- The version is part of the path: `/api/v1/...`.
- There are **no unversioned `/api/*` routes**. Clients must use `/api/v1`.
- Breaking changes go to a new version (`/api/v2`). `v1` stays stable and
  keeps its behaviour; only backwards-compatible additions (new optional
  fields, new endpoints) are made to `v1`.
- Controllers live under `App\Http\Controllers\Api\V1` and resources under
  `App\Http\Resources\Api\V1`, so a future `V2` can sit next to `V1`.

## Authentication

Sanctum bearer tokens. No session, no cookies.

1. Log in with a username or email plus password. The `login` field is a
   username or an email, picked by whether it contains `@`, exactly like the
   web login. 5 failed attempts per login + IP are allowed, then the login
   is throttled (429).
2. Send the token on every other request:

   ```
   Authorization: Bearer <token>
   ```

3. Log out to revoke the current token (`POST /api/v1/logout`).

Tokens do not expire by default (Sanctum default). A token is created per
login and named `flutter-app`.

## Endpoints

| Method | Path | Auth | Description |
| --- | --- | --- | --- |
| POST | `/api/v1/login` | No | Log in, get a token and the user |
| POST | `/api/v1/logout` | Yes | Revoke the current token |
| GET | `/api/v1/user` | Yes | The signed-in user |
| GET | `/api/v1/dashboard` | Yes | Counts and amounts for the signed-in user |
| GET | `/api/v1/technicians` | Yes | Technicians for the assign picker |
| GET | `/api/v1/devices` | Yes | List orders, paginated, with search and filters |
| POST | `/api/v1/devices` | Yes | Create an order |
| GET | `/api/v1/devices/{device}` | Yes | One order with progress logs and transactions |
| PUT | `/api/v1/devices/{device}` | Yes | Full update of an order |
| PATCH | `/api/v1/devices/{device}/status` | Yes | Change only the repair status |
| POST | `/api/v1/devices/{device}/assign` | Yes | Assign an order to a technician |
| POST | `/api/v1/devices/{device}/complete` | Yes | Mark an order completed |
| DELETE | `/api/v1/devices/{device}` | Yes | Delete an order (admin only) |

### Login

```
POST /api/v1/login
Content-Type: application/json

{"login": "miki", "password": "secret"}
```

Response `200`:

```json
{
  "user": {"id": 1, "name": "Miki", "username": "miki", "email": "miki@example.com", "role": "admin"},
  "token": "1|AbCdEfGh..."
}
```

Wrong password: `401 {"message": "These credentials do not match our records."}`.
Too many attempts: `429 {"message": "Too many login attempts...", "retry_after": 60}`.

### Create an order

```
POST /api/v1/devices
Authorization: Bearer <token>
Content-Type: application/json

{
  "client_name": "Miki",
  "client_number": "0912345678",
  "amount": 1000,
  "device_type": "mobile",
  "device_model": "iPhone 13",
  "serial_number": "SN-12345678",
  "imei": "356789012345678",
  "issue_description": "Screen cracked",
  "repair_status": "pending",
  "assigned_to": 3,
  "assign_role": "hardware_technician"
}
```

Response `201` with the created order (same shape as above). The
`order_number` (`TPB-xxxxx`) is generated by the server, 5 random digits,
unique. `assign_role` is a form-only field and is not stored.
`assigned_to` must be a technician; if `assign_role` is given it must
match that technician's role. If technicians of the chosen type exist, one
must be chosen; if none exist yet, the order may be created unassigned.

### Update an order

```
PUT /api/v1/devices/12
Authorization: Bearer <token>
Content-Type: application/json

{"client_name": "Miki", "client_number": "0912345678", "amount": 1200, "device_type": "mobile", "device_model": "iPhone 13", "repair_status": "in_progress"}
```

Full update, same validation as create (all required fields must be sent).
Response `200` with the updated order.

### Change only the status

```
PATCH /api/v1/devices/12/status
Authorization: Bearer <token>
Content-Type: application/json

{"repair_status": "in_progress"}
```

Response `200` with the updated order. This is the call a technician uses
to move their own assigned order along without sending a full payload.

### Assign an order

```
POST /api/v1/devices/12/assign
Authorization: Bearer <token>
Content-Type: application/json

{"assigned_to": 3, "assign_role": "hardware_technician"}
```

Response `200` with the updated order. Only admin or reception can assign.

### Complete an order

```
POST /api/v1/devices/12/complete
Authorization: Bearer <token>
```

Response `200`:

```json
{"message": "Device marked as completed successfully.", "data": { "...order..." }}
```

Only the `repair_status` changes to `completed`, exactly like the web
"mark as completed" action. No transaction is created here.

### Delete an order

```
DELETE /api/v1/devices/12
Authorization: Bearer <token>
```

Response `200 {"message": "Device deleted successfully."}`. Admin only.

## Roles

What each role can do through the API. The checks are enforced on the
server, in `DevicePolicy` and in the controllers, not only hidden in the
app. The list itself is also scoped: a technician only ever sees orders
assigned to them.

| Action | Admin | Hardware technician | Software technician | Reception |
| --- | --- | --- | --- | --- |
| Log in, view own user | Yes | Yes | Yes | Yes |
| List / view orders | All | Only assigned to them | Only assigned to them | All |
| Create an order | Yes | Yes | Yes | Yes |
| Update an order (full) | Yes | Only assigned to them | Only assigned to them | No (403) |
| Change status only | Yes | Only assigned to them | Only assigned to them | No (403) |
| Complete an order | Yes | Only assigned to them | Only assigned to them | No (403) |
| Assign an order | Yes | No (403) | No (403) | Yes |
| Delete an order | Yes | No (403) | No (403) | No (403) |
| Dashboard | All orders | Own assigned orders | Own assigned orders | All orders |
| Dashboard user counts | Yes | No | No | No |
| Manage users | No endpoint | No endpoint | No endpoint | No endpoint |

Notes:

- Any authenticated user can create an order, exactly like the web.
  `DevicePolicy::create()` returns true for every authenticated user.
- Reception can add an order and assign it, and can view orders read-only,
  but cannot edit, complete, delete, bulk change or export.
- There is no user-management endpoint in the API. Users are managed in
  the web app at `/admin/users` (admin only).

## Errors

All errors are JSON.

| Status | Meaning | Example |
| --- | --- | --- |
| 401 | No token, bad token, or wrong password | `{"message": "Unauthenticated."}` |
| 403 | Signed in, but the role or assignment does not allow it | `{"message": "This action is unauthorized."}` |
| 404 | Order or user not found | `{"message": "No query results for model [App\\Models\\Device] 99"}` |
| 422 | Validation failed, field errors are listed | See below |
| 429 | Too many login attempts | `{"message": "Too many login attempts...", "retry_after": 60}` |

Validation error shape (Laravel standard):

```json
{
  "message": "The phone number must be a valid Ethiopian mobile number starting with 09 or 07 and 10 digits long.",
  "errors": {
    "client_number": ["The phone number must be a valid Ethiopian mobile number starting with 09 or 07 and 10 digits long."]
  }
}
```

### Field rules (create / full update)

| Field | Rule |
| --- | --- |
| `client_name` | Required, string, max 255 |
| `client_number` | Required, Ethiopian mobile: starts `09` or `07`, exactly 10 digits |
| `amount` | Required, number, min 0, max 999999.99 |
| `device_type` | Required, one of `mobile`, `laptop`, `tablet`, `pc`, `mac`, `other` |
| `device_model` | Required, string, max 255 |
| `serial_number` | Optional, string, max 100 |
| `imei` | Optional, string, max 100 |
| `issue_description` | Optional, string, max 500 |
| `repair_status` | Required, one of `pending`, `in_progress`, `completed`, `cancelled`, `delivered` |
| `assign_role` | Optional, one of `hardware_technician`, `software_technician` (form-only, not stored) |
| `assigned_to` | Optional, must be an existing user who is a technician |

## Pagination and filters

`GET /api/v1/devices` accepts:

| Parameter | Description |
| --- | --- |
| `search` | Text search across client name, client number, order number, device model, serial number, IMEI and issue |
| `status` | One of `pending`, `in_progress`, `completed`, `cancelled`, `delivered` |
| `device_type` | One of `mobile`, `laptop`, `tablet`, `pc`, `mac`, `other` |
| `date_range` | One of `today`, `yesterday`, `this_week`, `last_week`, `this_month`, `last_month`, `custom` |
| `date_from`, `date_to` | `Y-m-d` dates, required when `date_range=custom` (inclusive) |
| `amount_min`, `amount_max` | Numbers, min 0 |
| `sort_by` | One of `created_at`, `amount`, `client_name`, `order_number` (default `created_at`) |
| `sort_dir` | `asc` or `desc` (default `desc`) |
| `per_page` | Default 20, min 1, max 100 |

`last_week` is the previous Monday to Sunday and `last_month` is the
previous calendar month. Results are ordered by the sort field, then by id
descending.

## Curl examples

```bash
# Log in and save the token
TOKEN=$(curl -s -X POST https://item-manager.thephoneboss.net/api/v1/login \
  -H "Content-Type: application/json" \
  -d '{"login": "miki", "password": "secret"}' | python3 -c "import sys, json; print(json.load(sys.stdin)['token'])")

# List pending mobile orders
curl "https://item-manager.thephoneboss.net/api/v1/devices?status=pending&device_type=mobile" \
  -H "Authorization: Bearer $TOKEN"

# Create an order
curl -X POST https://item-manager.thephoneboss.net/api/v1/devices \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"client_name": "Miki", "client_number": "0912345678", "amount": 1000, "device_type": "mobile", "device_model": "iPhone 13", "repair_status": "pending"}'

# Assign it, then complete it
curl -X POST https://item-manager.thephoneboss.net/api/v1/devices/12/assign \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"assigned_to": 3, "assign_role": "hardware_technician"}'
curl -X POST https://item-manager.thephoneboss.net/api/v1/devices/12/complete \
  -H "Authorization: Bearer $TOKEN"

# Dashboard
curl https://item-manager.thephoneboss.net/api/v1/dashboard \
  -H "Authorization: Bearer $TOKEN"
```
